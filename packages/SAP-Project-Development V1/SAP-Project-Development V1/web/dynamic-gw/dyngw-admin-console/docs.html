1 · The URL

Everything in this service is one endpoint. You never call a table or a function module directly — you call an action on the CallLog entity set, and the gateway decides whether you are allowed to do what you asked.

The proxy adds Basic Auth, the CSRF token and the cookie jar for you.

Base

Base URL
http://localhost:8774/api/dyngw
Three ways to get the URL wrong, all of which look like something else:
  • The repository segment is srvd_a2x, not srvd.
  • ?sap-client=100 goes on every call, ADT REST included. Without it you get a 401 that reads like a bad password (L-253/L-325).
  • If your query string already carries sap-client, do not append another — SAP answers 400 URI syntax, not a no-op.

Shape of every action call

Pattern
POST http://localhost:8774/api/dyngw/CallLog/com.sap.gateway.srvd_a2x.zfs_sd_dyngw.v0001.<ActionName>?sap-client=100

That namespace is fixed for this service. The six action names go where <ActionName> is.

2 · Your first call, step by step

This sequence is proved live against DS4_100_NIIF. T000 is registered on this system today, which makes it the cheapest liveness check you have.

Get a CSRF token and the session cookie

Only writes need the token — a plain GET of /Registry or /CallLog does not. Every action is a POST, so you need it. Skip this step entirely when calling through this console's proxy: it holds the token and cookie jar for you.

Request
GET http://localhost:8774/api/dyngw/$metadata?sap-client=100
X-CSRF-Token: Fetch

Keep the x-csrf-token response header and the session cookie. Both go on every subsequent write.

Read three rows from a registered table

Request
POST http://localhost:8774/api/dyngw/CallLog/com.sap.gateway.srvd_a2x.zfs_sd_dyngw.v0001.RunQuery?sap-client=100
Content-Type: application/json
X-CSRF-Token: <token>

{
  "TargetName": "T000",
  "FieldsJson": "[\"MANDT\",\"MTEXT\"]",
  "FilterJson": "",
  "OrderByJson": "",
  "MaxRows": 3,
  "SkipRows": 0,
  "RequestId": ""
}
Note the escaping. FieldsJson is a string that happens to contain JSON — one level of escaping in a single-shot call, and three inside a batch step. Build the innermost value first and let your serialiser escape it; message 022 cannot tell you which level broke.

Check the answer — and do not stop at HTTP 200

A refusal is HTTP 200 with ExecStatus:"E", not an HTTP error. Read the field, not the status code.

Response (abridged)
{
  "ExecStatus": "S",
  "ErrorCategory": "",
  "ResultCount": 3,
  "RowsJson": "[{\"MANDT\":\"000\",\"MTEXT\":\"SAP SE\"}, ...]",
  "GwUuid": "5254001f-e7a2-...",
  "IsCommitted": "X",
  "IsRolledBack": ""
}

Look at what it wrote to the log

Every call writes one CallLog row and one CallStep row per step. Use GwUuid from the response as the key.

Request
GET http://localhost:8774/api/dyngw/CallLog(<GwUuid>)?$expand=_Steps&sap-client=100

Or open it on the linkage report, which does exactly this read and lets you walk from the call to its steps to the registry rows that authorised them.

The same first call in PowerShell

PowerShell 5.1
# Through the proxy: no token, no credentials, no TLS fuss.
$base = "http://localhost:8774/api/dyngw"
$ns   = "com.sap.gateway.srvd_a2x.zfs_sd_dyngw.v0001"

# Build the inner JSON by hand: ConvertTo-Json collapses a 1-element array to an
# object, and the gateway then answers "Invalid JSON" (L-315).
$body = @{
  TargetName  = "T000"
  FieldsJson  = '["MANDT","MTEXT"]'
  FilterJson  = ""
  OrderByJson = ""
  MaxRows     = 3
  SkipRows    = 0
  RequestId   = ""
} | ConvertTo-Json

$r = Invoke-RestMethod -Method Post -ContentType "application/json" `
      -Uri "$base/CallLog/$ns.RunQuery?sap-client=100" -Body $body

$r.ExecStatus            # S
$r.RowsJson | ConvertFrom-Json

3 · Reading the answer

Every one of the six actions returns the same result shape. Two fields answer two different questions, and confusing them is the commonest mistake.

FieldWhat it tells you
ExecStatusS = the dispatch worked. E = it did not. Not "the business operation succeeded".
ErrorCategoryCLIENT your request was wrong · AUTH not permitted · TARGET the target failed technically · BUSINESS dispatched fine, but the target's own RETURN reported an error. ExecStatus S + BUSINESS means it ran and failed.
RowsJsonQuery results, as a JSON string.
ExportJson / TablesJsonA function module's EXPORT and TABLES parameters, as JSON strings.
StepsJsonPer-step detail — populated for ExecuteBatch only. A single-shot action leaves it empty; read the step from /CallLog(<GwUuid>)?$expand=_Steps instead.
MessageNo / MessageTextOn a single-shot refusal this is the generic 045 "batch aborted at step 1", truncated. The real reason (017, 018, 022, 035, 039…) is on the step row, not here (L-478).
IsCommitted / IsRolledBackX or blank. Only on this response — they were never added to the persisted CallLog entity, so no later GET can recover them (L-525).
ReplayedX = answered from the idempotency log; nothing re-executed.
GwUuidThe key of the CallLog row this call wrote. Keep it.
A refusal is HTTP 200. ExecStatus:"E" with a message is the normal refusal shape. An aborted batch is the exception — that returns 400, with the reason in the body.

The six actions

RunQuery

readA dynamic SELECT against a registered table or CDS view. Step kind QURY.
POST · RunQuery
POST http://localhost:8774/api/dyngw/CallLog/com.sap.gateway.srvd_a2x.zfs_sd_dyngw.v0001.RunQuery?sap-client=100

{
  "TargetName":  "ZFS_CDS_SLC_001",
  "FieldsJson":  "[\"ZOTTK_NO\",\"ZSTR\",\"ZOTTK_VALUE\"]",
  "FilterJson":  "[{\"field\":\"ZOTTK_ST\",\"op\":\"EQ\",\"value\":\"01\"}]",
  "OrderByJson": "[{\"field\":\"ZOTTK_NO\",\"desc\":false}]",
  "MaxRows":     100,
  "SkipRows":    0,
  "RequestId":   ""
}
  • Always send FieldsJson. The all-columns default breaks on any table with a DDIC .INCLUDE, and such fields are refused outright.
  • The target must be registered with TargetKind QURY. A row registered TABL is refused with 017 even though it is active and readable — "registered" and "usable by this action" are different questions (L-526).
  • MaxRows: 0 on the registry row means "this target sets no override", never "unlimited".

ExecuteTableCrud

writesDynamic INSERT / MODIFY / DELETE on a registered table. Step kind TABL.
POST · ExecuteTableCrud
POST http://localhost:8774/api/dyngw/CallLog/com.sap.gateway.srvd_a2x.zfs_sd_dyngw.v0001.ExecuteTableCrud?sap-client=100

{
  "TargetName":   "ZFS_SLC_OTTK_BTP",
  "Operation":    "INSERT",
  "ImportJson":   "[{\"ZOTTK_NO\":\"\",\"ZSTR\":\"DSX\",\"ZOTTK_VALUE\":1000000}]",
  "GenerateJson": "{\"Uuid\":[\"UUID\"],\"NumberRange\":[\"ZOTTK_NO\"],\"SysFields\":\"AUDIT\"}",
  "RequestId":    ""
}
MODIFY is a full-row replace, not a merge (L-520). Every column your payload omits is written back initial — create-audit fields included. Read the row, change what you mean to change, and send the whole thing back. This is the single most destructive mistake available in this API.
  • GenerateJson lets the server fill fields you cannot: Uuid (a fresh sysuuid_x16), NumberRange (from the registry row's one GenNrObject), SysFields:"AUDIT" (the five RAP audit fields).
  • Generation needs both permissions: the registry row must carry AllowGen, and the call must name the fields. There is no "generate everything allowed" shortcut. Refused with 052 otherwise.
  • Under CommitMode "NEVER" a NumberRange draw is refused (054) — a dry run will not gamble on whether a drawn number survives.
  • A primary-key collision on INSERT is absorbed as a partial-write success (message 048, severity W), not a failure. Check the step.

CallFunctionModule

writesA dynamic CALL FUNCTION against a registered function module. Step kind FUNC.
POST · CallFunctionModule
POST http://localhost:8774/api/dyngw/CallLog/com.sap.gateway.srvd_a2x.zfs_sd_dyngw.v0001.CallFunctionModule?sap-client=100

{
  "TargetName": "BAPI_SOMETHING_GETDETAIL",
  "ImportJson": "{\"DOCUMENTNUMBER\":\"0000012345\"}",
  "TablesJson": "{\"RETURN\":[]}",
  "RequestId":  ""
}
An output-only TABLES parameter must be sent as [] or its content never comes back (L-314). RETURN is the one people forget, and forgetting it means you cannot see the BAPI's own error.
  • Every FUNC target must be registered AllowWrite: true, even a read-only function module — the handler cannot tell reading from writing, so it demands the stronger right and fails closed (L-491). Do not read AllowWrite on a FUNC row as evidence that it writes.
  • Call mode decides whether a rollback reaches it. L = local, inside the LUW, undone by a rollback. R = RFC, which commits the caller's LUW and is outside any rollback. Blank falls back to TFDIR-FMODE, so any remote-enabled BAPI resolves to R (L-492).
  • CallFunctionModule never commits. A creating BAPI needs ExecuteBatch with a CommitMode, and ExecStatus:"S" only means the dispatch worked — parse RETURN.

SubmitReport

writesRuns an executable report in its own session and captures the list. Step kind SUBM.
POST · SubmitReport
POST http://localhost:8774/api/dyngw/CallLog/com.sap.gateway.srvd_a2x.zfs_sd_dyngw.v0001.SubmitReport?sap-client=100

{
  "TargetName": "Z_SOME_REPORT",
  "Operation":  "",
  "ImportJson": "{\"CaptureMode\":\"SALV\"}",
  "FilterJson": "[{\"name\":\"S_BUKRS\",\"sign\":\"I\",\"option\":\"EQ\",\"low\":\"1000\"}]",
  "MaxRows":    500,
  "RequestId":  ""
}
SUBM runs outside the rollback, always — its own RFC session commits independently. It also cannot share a batch with any in-LUW write step; that mix is refused in phase 1 with message 020.
  • Qualify a report before registering it: a CL_GUI_* reference in WBCROSSGT is a hard disqualifier, and an OBLIGATORY select-option must be supplied.
  • No report is registered or smoke-tested against v2 as of today. If you are the first, treat it as establishing the behaviour rather than confirming it.

RegisterTarget

adminAdds or widens an allow-list row. Step kind REGI. Needs ZFS_DYNGW ACTVT 01/02.
POST · RegisterTarget
POST http://localhost:8774/api/dyngw/CallLog/com.sap.gateway.srvd_a2x.zfs_sd_dyngw.v0001.RegisterTarget?sap-client=100

{
  "TargetName": "T001",
  "Operation":  "INSERT",
  "ImportJson": "{\"TargetKind\":\"QURY\",\"Operation\":\"SELECT\",\"IsActive\":true,\"AllowRead\":true,\"MaxRows\":20}",
  "RequestId":  ""
}
  • Operation here is the registry operation: INSERT (the default) fails with 035 if the target already exists. Widening an existing row must be typed out as UPDATE — that asymmetry is deliberate, so a registration is never widened by accident.
  • Booleans are Edm.Boolean: send true/false unquoted, never "X" — "X" is a 400 XML parse error, not a clean refusal (L-475).
  • Self-protection: anything matching ZFS_T_DYN_*, ZFS_RFC_DYN_* or the authorization object is refused with 039, writing nothing. This is the fix for v1's privilege-escalation hole, proved live.
  • Or just use the registry screen in this console, which does the same thing through POST /Registry and shows you the audit row it produced.

ExecuteBatch

writesMany steps, one transaction. Every other action is internally a one-step batch.
POST · ExecuteBatch
POST http://localhost:8774/api/dyngw/CallLog/com.sap.gateway.srvd_a2x.zfs_sd_dyngw.v0001.ExecuteBatch?sap-client=100

{
  "CommitMode": "AUTO",
  "RequestId":  "my-stable-key-0001",
  "StepsJson":  "[{\"index\":1,\"kind\":\"REGI\",\"targetname\":\"T001\",\"importjson\":\"{\\\"TargetKind\\\":\\\"QURY\\\",\\\"AllowRead\\\":true}\"},{\"index\":2,\"kind\":\"QURY\",\"targetname\":\"T001\",\"fieldsjson\":\"[\\\"MANDT\\\"]\",\"maxrows\":5}]"
}
Count the escaping levels. The body is JSON; StepsJson is a string containing JSON; a step's own ImportJson/FieldsJson is a string containing JSON inside that. Three levels. Build innermost-first and let the serialiser escape — deep action parameters do not work on this release, which is why this is a string and not an array (L-472).
  • Phase 1 validates every step before phase 2 executes any. A validation failure means nothing ran: every other step reports Severity "P" (planned).
  • A later step may use a target an earlier REGI step declared — that is how one call provisions a whole system.
  • You may not mix an out-of-LUW step with an in-LUW write. Out-of-LUW means every SUBM step and any FUNC step in call mode R — which is the default. Refused in phase 1, message 020. Fix by splitting the call, or registering the FUNC target with CALL_MODE "L".
  • CommitMode: AUTO commits if every step succeeded · NEVER is a dry run · ALWAYS is currently identical to AUTO; do not assume it does more.
  • An aborted batch returns HTTP 400 with the reason in the body, and rolls back — proved live, both phases (L-496). Even so: verify by re-reading what you wrote rather than trusting ExecStatus alone.

Step kinds

Inside a batch you name a kind rather than an action. This is also what a registry row's TargetKind must match.

KindDoesNeeds AllowWriteRolled back on abort
QURYdynamic SELECTnon/a — nothing written
TABLINSERT / MODIFY / DELETEyesyes
FUNCCALL FUNCTIONalways, even read-only (L-491)only in call mode L; blank defaults to R (L-492)
SUBMSUBMIT a reportalwaysno — its own session
REGIregister / update an allow-list rowgated by the authorization object, not the allow-listyes

Reading the log tables

Four entity sets, plain GET, no CSRF token needed. This is what the linkage report reads.

Useful reads
# the allow-list
GET http://localhost:8774/api/dyngw/Registry?$orderby=TargetName&sap-client=100

# one call with its steps
GET http://localhost:8774/api/dyngw/CallLog(<CallUuid>)?$expand=_Steps&sap-client=100

# every step that ran against one registry row
GET http://localhost:8774/api/dyngw/CallStep?$filter=RegUuid eq <RegUuid>&sap-client=100

# who changed the allow-list, and what it looked like before
GET http://localhost:8774/api/dyngw/RegistryHistory?$orderby=ChangedAt desc&$top=50&sap-client=100

# how many rows, without fetching any
GET http://localhost:8774/api/dyngw/CallStep?$top=0&$count=true&sap-client=100
JoinMeaning
Registry.RegUuid → CallStep.RegUuidthe allow-list row that authorised this step
CallLog.CallUuid → CallStep.CallUuidthe steps of this call
Registry.RegUuid → RegistryHistory.RegUuidevery change made to this allow-list row
RegistryHistory.CallUuid → CallLog.CallUuidthe gateway call that made the change
A target-scoped auditor sees steps but an empty call log. CallStep carries a target name so its DCL restricts genuinely; CallLog does not, so its grant needs full ZDYNTGT scope. An empty /CallLog next to a populated /CallStep is this, not data loss.

Idempotency

Send a stable, unique RequestId on anything you might retry. A repeat with the same id is answered from the stored row — Replayed:"X", the same GwUuid, nothing re-executed.

Omitting RequestId is opting out, not a shortcut. A blank id is stored as the row's own CallUuid, so it is unique by construction and never matches a previous blank-id call.

Things that will bite you

SymptomWhat is actually happening
401 that looks like a bad passwordsap-client=100 missing from the URL.
HTTP 200 but nothing happenedA refusal. Read ExecStatus, then the step's message — the header's 045 is generic.
Message 017 on a target you can see in the registryThe row's TargetKind does not match the step kind your action dispatches. RunQuery needs QURY, not TABL (L-526).
Message 018 on a read-only function moduleEvery FUNC target needs AllowWrite (L-491).
Message 022 and no idea which fieldA *Json escaping level is wrong. It cannot tell you which one; build innermost-first.
Message 039You tried to register a framework object. By design, and it writes nothing.
400 XML parse error on a booleanYou sent "X". These are Edm.Boolean: true/false, unquoted (L-475).
Columns silently blanked after an updateExecuteTableCrud MODIFY is a full-row replace (L-520). Resend the whole row.
A batch "rolled back" but the FM's work survivedThat step ran in call mode R — outside the LUW. Blank is R for any remote-enabled FM (L-492).
Fresh system answers 017 to everythingAllow-list rows are deliveryClass #A application data and do not travel with a transport. Register targets on the new system.
A role "covering everything" grants more than intendedZDYNTGT maintained as a range brackets the literal *. Single values only (L-441).
