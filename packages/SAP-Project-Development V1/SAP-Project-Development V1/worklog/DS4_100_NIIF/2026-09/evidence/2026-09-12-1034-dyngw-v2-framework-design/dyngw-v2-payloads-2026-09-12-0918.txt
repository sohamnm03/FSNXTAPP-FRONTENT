Action namespace:
  com.sap.gateway.srvd_a2x.zfs_sd_dyngw.v0001
Entity sets:
  CallLog, CallStep, Registry, RegistryHistory
Actions (all six are "static action" on ZFS_R_DynGwCallTP, bound to CallLog per task-18's own

  RunQuery, CallFunctionModule, ExecuteTableCrud, SubmitReport, RegisterTarget, ExecuteBatch
Every request URL carries sap-client=100 (L-253/L-325). A write needs the X-CSRF-Token obtained
from a prior GET .../$metadata?sap-client=100 with header X-CSRF-Token: Fetch, and the session
cookie that GET returns (L-... none specific, but standard SAP CSRF protocol).

Parameter shapes, from the plan (docs/superpowers/plans/2026-09-12-1032-dyngw-v2.md lines 1744-1751)
and confirmed live in task-18-report.md:

  RunQuery           TargetName, FieldsJson, FilterJson, OrderByJson, MaxRows, SkipRows, RequestId
  CallFunctionModule TargetName, ImportJson, TablesJson, RequestId
  ExecuteTableCrud   TargetName, Operation, ImportJson, RequestId
  SubmitReport       TargetName, Operation, ImportJson, FilterJson, MaxRows, RequestId
  RegisterTarget     TargetName, Operation, ImportJson, RequestId
  ExecuteBatch       CommitMode, RequestId, StepsJson (string; JSON array of step objects)

Each StepsJson entry mirrors ZFS_AE_DynGwStep: Kind, TargetName, Operation, ImportJson,
TablesJson, FieldsJson, FilterJson, OrderByJson, MaxRows, SkipRows - so a batch payload nests
JSON two levels deep (StepsJson is a string containing an array of objects, each of whose *Json
fields is itself a string containing JSON), matching L-472's cost/benefit note (v1 nested three
levels; v2 nests two).

Result shape (ZFS_AE_DynGwResult), returned as the top-level JSON object of the action response:
  GwUuid, ExecStatus, ErrorCategory, Replayed, MessageId, MessageNo, MessageText, ResultCount,
  DurationMs, RowsJson, ExportJson, TablesJson, StepsJson

21. PROOF 1 (L-350 closure) - literal brief form: two TABL INSERT, same primary key
===============================================================================================
Shape (needs -ProbeTable/-ProbeKeyField/-ProbeKeyValue):
{"CommitMode":"AUTO","RequestId":"T20-PROOF1-TABL-0001","StepsJson":"[{\"Kind\":\"TABL\",\"TargetName\":\"<ProbeTable>\",\"Operation\":\"INSERT\",\"ImportJson\":\"[{\\\"<ProbeKeyField>\\\":\\\"<value>\\\"}]\",\"TablesJson\":\"\",\"FieldsJson\":\"\",\"FilterJson\":\"\",\"OrderByJson\":\"\",\"MaxRows\":0,\"SkipRows\":0},{... identical step again ...}]"}

*** CRITICAL FINDING FROM READ-ONLY SOURCE REVIEW (2026-09-13, ZCL_FS_DYN_RUNTIME~MODIFY_TABLE
and ZCL_FS_DYN_HDL_TABLE~ZIF_FS_DYN_HANDLER~EXECUTE, both read via getObjectSource) ***
INSERT is issued as "INSERT (target_table) FROM TABLE <rows> ACCEPTING DUPLICATE KEYS." A
duplicate on the table's PRIMARY KEY is therefore NOT an exception - it is sy-subrc=4,
sy-dbcnt=0, and the handler reports it as a PARTIAL WRITE: ExecStatus S, severity W, message 048
("<table>: 0 of 1 row(s) written"). The batch does NOT abort and DOES commit step 1's row.
This means the brief's literal "two TABL INSERT steps, same key" scenario will most likely
return ExecStatus S, not E, if <ProbeKeyField> is the table's primary key - the opposite of what
the brief expects, and NOT a script defect. Reproducing a genuine phase-2 abort via TABL needs a
target whose SECONDARY unique index (not primary key) is violated by the second insert, since
ACCEPTING DUPLICATE KEYS only suppresses primary-key duplicates. No such non-framework table
was identified or created for this authoring pass (rule 3). See task-20-report.md for the
recommendation.

22. PROOF 1 (L-350 closure) - corroborating reproduction: two REGI steps, same target
===============================================================================================
Request (ZZPROOF1 is a synthetic name that resolves to nothing real; QURY is arbitrary):
{"CommitMode":"AUTO","RequestId":"T20-PROOF1-REGI-0001","StepsJson":"[{\"Kind\":\"REGI\",\"TargetName\":\"ZZPROOF1\",\"Operation\":\"INSERT\",\"ImportJson\":\"{\\\"TargetKind\\\":\\\"QURY\\\",\\\"IsActive\\\":true,\\\"AllowRead\\\":true,\\\"AllowWrite\\\":false,\\\"MaxRows\\\":10,\\\"LogLevel\\\":\\\"A\\\",\\\"Descr\\\":\\\"proof1 step1\\\"}\",\"TablesJson\":\"\",\"FieldsJson\":\"\",\"FilterJson\":\"\",\"OrderByJson\":\"\",\"MaxRows\":0,\"SkipRows\":0},{\"Kind\":\"REGI\",\"TargetName\":\"ZZPROOF1\",\"Operation\":\"INSERT\",\"ImportJson\":\"{\\\"TargetKind\\\":\\\"QURY\\\",\\\"IsActive\\\":true,\\\"AllowRead\\\":true,\\\"AllowWrite\\\":false,\\\"MaxRows\\\":10,\\\"LogLevel\\\":\\\"A\\\",\\\"Descr\\\":\\\"proof1 step2 - duplicate, must abort the batch\\\"}\",\"TablesJson\":\"\",\"FieldsJson\":\"\",\"FilterJson\":\"\",\"OrderByJson\":\"\",\"MaxRows\":0,\"SkipRows\":0}]"}

Source-verified mechanism (ZCL_FS_DYN_HDL_REGI~ZIF_FS_DYN_HANDLER~PREPARE, read via
getObjectSource): step 2's INSERT duplicate check calls ZCL_FS_DYN_REGISTRY=>EXISTS, which
"deliberately sees ... an earlier REGI step's declaration" - i.e. step 1's own PENDING buffer
from declare_pending(). So step 2 fails in PHASE 1 (validation), before ANYTHING has executed,
with message 035. The dispatcher's phase-1 failure path (ZCL_FS_DYN_DISPATCH~RUN) then calls
rollback_luw() (a no-op, since nothing ran) and reports the call level as ExecStatus E, header
MessageId/No ZFS_TRM_MSG/045 naming step 2, MessageText carrying 035's rendered text. Neither
REGI step ever reaches EXECUTE, so ZFS_T_DYN_REG never receives a row for ZZPROOF1/QURY at all -
verified after the call via GET Registry?$filter=TargetKind eq 'QURY' and TargetName eq
'ZZPROOF1', expecting zero rows. This reproduces the L-350 guarantee (nothing survives an
aborted batch) with no write to any external table and no cleanup required - the duplicate is
refused before either row exists.

24. PROOF 3 - EXECUTE vs ADMIN split - BLOCKED, no payload sent
===============================================================================================
Needs a second SAP user/session holding ZFS_DYNGW ACTVT 16 (EXECUTE) only, not 01/02/03
(ADMIN). FS_DEV3 (the only credential in config/sap-systems.json for DS4_100_NIIF) holds all
four activities. No role, user or profile may be created to manufacture this (project rule 3),
and running as FS_DEV3 anyway would pass whether or not the control works, proving nothing.
Case shapes, ready the moment a restricted principal exists:
  - RegisterTarget for any new TargetName, as the restricted caller -> expect ExecStatus E,
    message 040.
  - ExecuteTableCrud INSERT against ZFS_T_DYN_REG, as the restricted caller -> expect
    ExecStatus E, message 039. (039 itself is exercised with FS_DEV3 in payloads #7/#12/#22
    above; what is NOT exercised is whether a caller with EXECUTE-only even reaches that check
    the same way, or is stopped earlier by the ADMIN gate - that is specifically what proof 3
    is for.)
