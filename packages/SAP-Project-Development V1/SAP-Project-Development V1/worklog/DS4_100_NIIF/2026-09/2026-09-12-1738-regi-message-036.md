- **Requested by:** human (vinit.s@fourthsignal.com)

## Scope

The human registered `BAPI_FTR_IRATE_DEALCREATE` with a `REGI` batch step, read the resulting
`ZFS_T_SLC_DYNGW` rows, and asked whether the gateway had **also called the BAPI** — because the
log row said *"BAPI_FTR_IRATE_DEALCREATE executed successfully, 1 row(s) affected"*. It had not.
That is message 026, which `REGI` was reusing, and it names `TARGET_NAME` — which for a `REGI`
step is the target being *registered*, not something executed (L-370).

They asked for message 036 to be added and wired up. That is the whole scope: no behaviour
change, no new object beyond the message.

## What changed

| Object | Type | Change |
|---|---|---|
| `ZFS_TRM_MSG` | MSAG/N | **new message 036** (type S): `Target &1 registered, &2 row(s) affected` |
| `ZCL_FS_SLC_GW_REGI` | CLAS/OC | `zif_fs_slc_gw_handler~execute` builds its own success outcome with 036 instead of calling `ZCL_FS_SLC_GW_BASE=>succeed( )`; new private constant `c_msg_registered` |

**`ZCL_FS_SLC_GW_BASE` was deliberately not touched.** The obvious alternative was an optional
`iv_number` parameter on `succeed( )` defaulting to `'026'`. That would be source-compatible, but
it puts a change on the foundation class every handler compiles against in order to serve the one
handler that needs a different message. `REGI`'s success genuinely *is* a different statement, so
assembling it in the handler that owns the semantics is the more honest placement — and it matches
the decision already recorded for `c_capture_job` in the 2026-09-11 lifecycle activity.

## Transport split — unresolved, and it matters

`E071` for `ZFS_TRM_MSG` shows `DS4K907019` and **`DS4K907194`**. It does **not** show
`DS4K907263`, which is where `ZCL_FS_SLC_GW_REGI` — the class that raises 036 — actually sits.

This is L-355 exactly: `transportInfo` reported the object already locked on `DS4K907018` / task
`DS4K907194` with an empty `TRANSPORTS` list, so the transport argument could not place it
anywhere else. Passing `DS4K907194` explicitly was therefore describing reality, not choosing it.

**Consequence:** import `DS4K907263` alone into QA or production and every `REGI` step there
resolves 036 to nothing. Release the two together, or reassign in `SE09` first. Reassigning
another user's open task is not something to do unasked, so it is flagged rather than done.
