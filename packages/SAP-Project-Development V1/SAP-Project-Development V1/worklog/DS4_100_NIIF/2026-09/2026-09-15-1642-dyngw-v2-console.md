### A real bug found and fixed during Step 7 verification

The reference proxy (`ottk-dttk-console/proxy.py`, copied verbatim per the brief) hard-codes
`Accept: application/json` on every outbound request, and always appends
`&sap-client=<client>` to the query string. Both are silently correct for the four
data-only services the reference console calls, but both break the mandated `$metadata`
verification call in this task:

1. `$metadata` in OData v4 is XML-only. Forcing `Accept: application/json` on it gets a 406
   from SAP (`/IWCOR/CX_OD_NOT_ACCEPTABLE`), confirmed by testing the same URL directly
   against SAP with `Accept: application/xml` (200) vs. the proxy's forced json Accept (406).
2. The brief's own verification URL already carries `?sap-client=100`. The proxy's
   `_service_url` then appends `&sap-client=100` again unconditionally, producing a
   duplicate query parameter that SAP refuses with a 400
   (`/IWCOR/CX_OD_URI_SYNTAX_ERROR`).

Both were fixed **only in `web/dyngw-v2-console/proxy.py`** (not in the seven other consoles,
which were touched only for the docstring/404-text updates named in the brief):
- `attempt()` now sends `Accept: application/xml` when the forwarded path ends in
  `$metadata`, and `application/json` otherwise.
- `_service_url()` no longer appends `sap-client=` if the incoming query string already
  contains it.

After both fixes, `GET /api/dyngw/$metadata?sap-client=100` returns 200 with the expected
fields present (grep against the raw metadata XML, not just an unstructured field-name
match -- `GenerateJson` was verified as a `<Parameter>` inside the `<Action Name=
"ExecuteTableCrud">` element, and `IsCommitted`/`IsRolledBack` as `<Property>` entries inside
`<ComplexType Name="ZFS_AE_DynGwResult">`, its `ReturnType`).

This is a plumbing bug in the copied proxy code, not a gap in Phase 1's ABAP work, so it did
not need to be reported as blocked -- it was fixable within the scope of this console's own
file.

## Two findings that changed the plan (both live-verified, both in the ledger)

- **L-525** -- `CallLogType` (the `CallLog` entity behind this panel's own read) has no
  `IsCommitted`/`IsRolledBack` properties at all; those live only on the `ZFS_AE_DynGwResult`
  action-response type. The call-log table renders both columns as `n/a` with an explanatory
  tooltip rather than silently dropping them or guessing from `ExecStatus`.
- **L-526** -- `ZFS_T_TRM_PROBE` is registered (`TABL`, `AllowRead` true) but `RunQuery` still
  refuses it live with 017, because `RunQuery`'s step kind is `QURY` and the registration is
  `TargetKind:"TABL"` -- a kind mismatch, not an availability problem. The `PROBE` counter shows
  "not registered" (the brief's own fallback text) with the true 017 kept in a tooltip.
- A related design choice (not a finding, a deliberate tradeoff): reading `PROBE` means an actual
  `RunQuery` through the gateway, which itself writes a new `CallLog`+`CallStep` row -- so, to
  avoid the trace panel polluting the very log it exists to show, `PROBE` is re-queried only on
  first page load and via the panel's own refresh button; every automatic refresh triggered by
  another action (list loads, provisioning, diagnostics) keeps the last known `PROBE` reading.
