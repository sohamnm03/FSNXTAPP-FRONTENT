- **Date:** 2026-09-12
- **System:** DS4_100_NIIF (`DS4` / client `100`)
- **Package:** `ZFS_DYN_GW` (exists, empty)
- **Transport:** `DS4K907263`
- **Requested by:** human (vinit.s@fourthsignal.com)
- **Status:** design approved in chat; spec awaiting human review
- **Relationship to earlier specs:** supersedes `2026-09-10-1520-gateway-framework-design.md` and
  `2026-09-12-0051-dyngateway-table-split-design.md` as the forward design. Neither is deleted —
  the running service `ZFS_SB_DYNGATEWAY_O4_API` still implements them and is **left untouched**.

---

## 1 · Why a rebuild rather than another repair

The live gateway works and its core ideas are right. What is wrong is structural, and two
successive repair attempts have now proved it cannot be fixed in place:

1. **Nothing owns the transaction.** The engine runs inside RAP *action* processing, where
   `COMMIT WORK` / `ROLLBACK WORK` are not merely inadvisable but a documented runtime error.
   Issuing them produced a live `BEHAVIOR_ILLEGAL_STATEMENT` dump that took the service down
   (2026-09-12). Without them, the durable-log RFC implicitly commits the caller's LUW, so an
   aborted batch's earlier writes survive (L-350 — open, and accepted as a gap).
   **Rollback and durable failure-logging are mutually exclusive in the current architecture.**
2. **The allow-list is not protected from the thing it guards.** `ZFS_T_SLC_DYNGW` is itself
   registered as a writable `TABL` target, so a caller with execute rights can insert an
   allow-list row and self-register any function module or report.
3. **Authorization is nominal.** The DCL is an unrestricted `grant select`; the behaviour pool
   grants create/update/delete unconditionally; `ZCL_FS_SLC_GW_REGPOL` is `OPEN`. Switching
   `REGI` to `AUTH` would not close ordinary OData CRUD, so there is no single place to tighten.
4. **The contract cannot absorb change.** Every action parameter is generated `Nullable="false"`.
   Adding the optional `RequestId` therefore made an eleventh field mandatory on every call and
   broke every existing caller — a change that was correct on paper and breaking in practice.

A fresh package lets all four be fixed at the root, with the running service untouched as a
fallback until the new one passes acceptance.

### 3.6 · Composition

`ExecuteBatch` mixes all five kinds in one call. **Validation runs for every step before any step
executes**; a batch that fails validation runs nothing at all and reports every step as `P`
(planned). Carried forward unchanged — and now with a real rollback behind it.

## 5 · Data model

Four tables. Each has one delivery class, one buffering setting, one retention policy and one
authorization profile — which is precisely what a single table cannot have, and the reason the
v1 model could not be tuned.

### 5.1 · `ZFS_T_DYN_REG` — the allow-list

Configuration: small, read on every dispatch, changed rarely.

| Field | Type | Purpose |
|---|---|---|
| `client` | `mandt` | key |
| `reg_uuid` | `sysuuid_x16` | key |
| `target_kind` | `ZFS_DE_DYN_KIND` | `FUNC` \| `TABL` \| `QURY` \| `SUBM` |
| `target_name` | `char(30)` | FM / table / CDS entity / report name |
| `operation` | `char(10)` | pins the row to one operation; blank = any |
| `is_active` | `abap_boolean` | kill switch — instant, no transport |
| `allow_read` / `allow_write` | `abap_boolean` | the two permissions a call is checked against |
| `call_mode` | `char(1)` | `FUNC` only: `R` \| `L` \| blank = auto |
| `max_rows` | `int4` | row ceiling; `0` = uncapped, a deliberate per-target decision |
| `log_level` | `ZFS_DE_DYN_LOGLVL` | `A` all \| `E` errors only \| `N` none |
| `descr` | `char(60)` | free text |
| + the 5 mandatory audit fields | | per `docs/ddic-table-template.md` — without them the RAP generators emit no ETag and no lock (L-218) |

- **Delivery class `C`** (decision 7). Log and history tables stay non-transportable.
- **Fully buffered** — possible only because the log no longer shares this table. `resolve` runs
  on every dispatch, so this is the single largest performance win available.
- **Unique index on `(client, target_kind, target_name)`.** This is what makes registration
  concurrency-safe; v1 used check-then-insert with no lock and no uniqueness guarantee.
- A lock object `EZFS_T_DYNREG` is created **only if** the Registry BO's generated locking
  requires one. Decided by `run_validation`, not assumed.

### 5.2 · `ZFS_T_DYN_REGH` — allow-list change history

Append-only. One row per change to `ZFS_T_DYN_REG`, from **any** route. Closes L-369.

| Field | Type | Purpose |
|---|---|---|
| `client`, `hist_uuid` | | key |
| `reg_uuid` | `sysuuid_x16` | the registry row affected |
| `change_type` | `char(1)` | `I` \| `U` \| `D` |
| `target_kind`, `target_name` | | denormalised, so a deleted row stays identifiable |
| `before_json` / `after_json` | `string` | the row either side; `before` empty on `I`, `after` empty on `D` |
| `source` | `char(4)` | `ODAT` (entity CRUD) \| `REGI` (action or batch step) |
| `call_uuid` | `sysuuid_x16` | the call that caused it, when there was one |
| `changed_by` / `changed_at` | | who and when |

Delivery class `A`. No update or delete exposed anywhere — history is not editable.

### 5.3 · `ZFS_T_DYN_CALL` — one row per HTTP call

| Field | Type | Purpose |
|---|---|---|
| `client`, `call_uuid` | | key; `call_uuid` is the `GwUuid` returned to the caller |
| `action` | `char(20)` | which of the six actions |
| `request_id` | `char(36)` | caller-supplied idempotency key (§8.1); blank if not sent |

## 6 · Runtime architecture

```
OData V4 action
      |
ZBP_FS_DYNGWCALLTP            thin: envelope, auth, budget, idempotency check only
      |                       no dynamic call, no COMMIT, no ROLLBACK, ever
      +-- CALL FUNCTION ZFS_RFC_DYN_EXECUTE DESTINATION 'NONE'
      |     ============== the execution session - its own LUW ==================
      |     |  ZCL_FS_DYN_DISPATCH                                              |
      |     |    +- ZCL_FS_DYN_AUTH       caller permissions (7.1)              |
      |     |    +- ZCL_FS_DYN_REGISTRY   allow-list, buffered + request cache   |
      |     |    +- ZCL_FS_DYN_BUDGET     bytes / steps / rows / time (8.2)     |
      |     |    +- ZCL_FS_DYN_FACTORY -> ZIF_FS_DYN_HANDLER                    |
      |     |    |     phase 1: prepare() every step  (validate, touch nothing) |
      |     |    |     phase 2: execute() every step  (same instance)           |
      |     |    |     ZCL_FS_DYN_HDL_QUERY / _FUNC / _TABLE / _SUBMIT / _REGI  |
      |     |    +- ZCL_FS_DYN_RUNTIME    the ONLY class doing dynamic work     |
      |     |    +- COMMIT WORK | ROLLBACK WORK       <- legal here             |
      |     ====================================================================
      |
      +-- ZCL_FS_DYN_LOG -> RAP transactional buffer -> save -> CALL + STEP rows
```

### 6.1 · Why the execution session

Two different LUWs is the whole design. Business work lives in the execution session's LUW, where
`ROLLBACK WORK` is legal because there is no RAP context. The log lives in the RAP LUW and is
committed by RAP's own save sequence. **Rollback and durable failure-logging stop competing**,
which is the thing v1 structurally cannot do.

A synchronous RFC implicitly commits the *caller's* LUW — the mechanism behind L-350. Here that
is harmless by construction: at the moment of the call the RAP side has written nothing, because
every write happens inside the session and every log row is written afterwards.

`SUBM` nests a second session (`ZFS_RFC_DYN_SUBMIT`) because a report may start its own LUW.

### 6.2 · Handler contract

`ZIF_FS_DYN_HANDLER`: `kind()`, `needs_write()`, `prepare( )` — validate only, never touch data —
and `execute( )`. **`prepare` and `execute` run on the same instance**, resolved once from the
factory. v1 re-`CASE`d on kind in both phases and allocated a second handler through static
wrappers, which is why "add a kind by adding a factory row" was documented but not true.

### 6.3 · Transaction outcomes

| Situation | Execution session | RAP LUW |
|---|---|---|
| All steps succeed, `CommitMode` `AUTO`/`ALWAYS` | `COMMIT WORK` | log row committed by RAP save |
| A step fails | `ROLLBACK WORK` — every `FUNC`/`TABL`/`REGI` write in the batch is undone | log row still written and committed |
| `CommitMode = NEVER` | `ROLLBACK WORK` regardless of outcome | log row still written |

The RAP action **never** calls `failed`/`reported` for a business outcome, so RAP always commits
the log. That is also what makes §7.3's HTTP discipline consistent.

### 6.4 · Documented limits

- A `SUBM` step owns its own session and LUW. Its writes are outside the rollback. Unchanged
  from v1, stated rather than discovered.
- A function module that issues its own `COMMIT WORK` internally ends the session's LUW early, so
  steps before it are no longer rollback-able. That is ABAP, not this design; the mitigation is
  registration review and `RequestId`.

## 7 · Contract, errors and authorization

### 7.1 · Authorization — `ZFS_DYNGW`

Fields: `ACTVT`, target kind, target-name pattern. Three genuinely separate permissions:

| Permission | Grants |
|---|---|
| `ADMIN` | maintain the allow-list — entity CRUD **and** `RegisterTarget`/`REGI` |
| `EXECUTE` | call registered targets; scopable by kind and by target-name pattern |
| `AUDIT` | read `/CallLog`, `/CallStep`, `/RegistryHistory` |

Enforced in **three places, so no route bypasses it**: the DCLs (replacing v1's unrestricted
`grant select`), the behaviour pools' `get_global_authorizations`/`get_instance_authorizations`
(replacing v1's unconditional grant), and `ZCL_FS_DYN_AUTH` inside the orchestrator.

**Framework self-protection, compiled and not configurable:** any target whose name matches
`ZFS_T_DYN_*`, `ZFS_RFC_DYN_*` or the authorization object itself is refused by *both*
`RegisterTarget`/`REGI` and `POST /Registry`. This closes the escalation path that exists today,
where `ZFS_T_SLC_DYNGW` is registered as a writable `TABL` target.

The service user's own SAP authorizations remain the effective ceiling on everything, and
`S_PROGRAM` is still checked before any `SUBMIT`.

### 7.2 · Error taxonomy

`ExecStatus` keeps its v1 meaning — "the dispatch worked". A **separate `ErrorCategory`** answers
the different question, "did the thing I asked for actually happen?":

| `ExecStatus` | `ErrorCategory` | Means | Who fixes it |
|---|---|---|---|
| `S` | *(blank)* | dispatched, and the target was happy | — |
| `S` | `BUSINESS` | dispatched fine, the target refused the business request (a BAPI returning `E`/`A` in `RETURN`) | the business user |
| `E` | `CLIENT` | the request was wrong (017, 022, 023, 024, 025) | the caller |
| `E` | `AUTH` | not permitted (018, 033, 040) | an administrator |
| `E` | `TARGET` | the gateway tried and the target failed technically (020) | the ABAP developer |

Callers that ignore `ErrorCategory` behave exactly as they do against v1. `severity`
(`S`/`W`/`E`/`A`) sits alongside it on every step row.

**Aggregation from step to call, so the two levels cannot disagree:** the call row's
`error_category` is the category of the **first step** whose severity is the highest reached in
that call, ranked `A > E > W > S`. A call with one `BUSINESS` step and one `TARGET` step therefore
reports `TARGET`, because a technical failure outranks a business refusal. When every step
succeeded the call row's category is blank. `exec_status` on the call row is `E` if any step is
`E`, otherwise `S` — so a `S`/`BUSINESS` call row means every dispatch worked and at least one
target said no.

`CATCH cx_root` is replaced throughout by typed catches, so a programming fault stops being
reported as "invalid JSON" — which is what v1's `ZCL_FS_SLC_GW_TABLE` and `_REGI` do today.

### 7.3 · HTTP status discipline

**HTTP status describes the protocol outcome; the payload describes the business outcome.**

| Situation | Status |
|---|---|
| Understood and processed, whatever the result | `200` + `ExecStatus` |
| Malformed request the service cannot parse | `400` |
| Not authenticated / not authorised | `401` / `403` |
| Unknown URL | `404` |

An aborted batch returns `200` with `ExecStatus='E'` and per-step detail — v1 returns `400`,
which conflates a business failure with a protocol failure and produced the "empty body on abort"
class of problem.

### 7.4 · OData surface

```
Base: /sap/opu/odata4/sap/zfs_sb_dyngw_o4_api/srvd_a2x/sap/zfs_sd_dyngw/0001
      ?sap-client=100 on EVERY url, $metadata included (L-253/L-325)

/Registry                          CRUD        the allow-list        (ADMIN)
/RegistryHistory                   read-only   who changed what      (AUDIT)
/CallLog                           read-only   one entity per call   (AUDIT)
/CallLog(<uuid>)?$expand=_Steps    read-only   header + every step
/CallStep                          read-only   cross-call step queries
```

Six actions, each with **its own parameter entity** — `RunQuery` no longer has to send
`StepsJson`:

| Action | Parameter entity |
|---|---|
| `RunQuery` | `ZFS_AE_DynGwQuery` |
| `CallFunctionModule` | `ZFS_AE_DynGwFunc` |
| `ExecuteTableCrud` | `ZFS_AE_DynGwTable` |
| `SubmitReport` | `ZFS_AE_DynGwSubmit` |
| `RegisterTarget` | `ZFS_AE_DynGwRegister` |
| `ExecuteBatch` | `ZFS_AE_DynGwBatch` + `ZFS_AE_DynGwStep` (composition) |

All six return `ZFS_AE_DynGwResult`.

`ExecuteBatch` takes `Steps` as a **real nested array** via a deep action parameter, so a batch
payload carries **one** level of JSON escaping instead of three. Only genuinely open-ended
payloads (`ImportJson`, `TablesJson`, `FieldsJson`, `FilterJson`, `OrderByJson`) remain JSON
strings, because their shape is the target's, not ours.

**Stated plainly in the contract, because discovering it live is what broke v1:** RAP generates
every action parameter as `Nullable="false"` and no CDS annotation changes that. Parameters are
therefore **structurally mandatory and semantically optional** — send the field as `""` or `0` to
mean "absent". Per-action entities reduce this from eleven fields on every call to four to six.

## 8 · Idempotency, budgets, retention

### 8.1 · Idempotency

`RequestId`, client-generated, ≤ 36 chars, blank = absent. On arrival, if a `ZFS_T_DYN_CALL` row
already carries that `request_id`, the gateway **executes nothing** and returns that call's stored
outcome with `Replayed='X'`. Uniqueness is a database index, so two concurrent retries cannot
both execute. Sending no `RequestId` behaves exactly as today.

This is what makes a creating BAPI behind a network timeout answerable instead of a guess.

### 8.2 · Budgets

Checked **before** expensive deserialization, and re-checked on decoded size:

| Budget | Default |
|---|---|
| Request bytes | 1 MB |
| Batch steps | 50 |
| Write rows per step | 1 000 |
| Response bytes | 4 MB |
| Wall-clock per call | 300 s |

The wall-clock budget is checked **between steps**, not as an interrupt — a single long-running
step is bounded by the target's own runtime limits, not by this. It exists to stop a 50-step batch
running for an hour, and the refusal names the step that would have exceeded it.

`MaxRows: 0` survives as a deliberate per-target choice (L-356), and `QURY` gains `Skip`. **A
`Skip` greater than zero requires a stable sort order, defined precisely as: `OrderByJson` must
end with the source's full primary key** (any additional leading sort fields are free). Without it
the database may return overlapping or missing rows across pages, so the request is refused with
message 042 rather than served incorrectly.

### 8.3 · Logging

**Decide, then serialize, then write** — the reverse of v1, which serializes and concatenates the
full payload before consulting `level_allows` and can then discard it. Caps are **byte-based with
an explicit `*_truncated` flag**, and cap a valid structured envelope rather than an arbitrary
substring; v1's cap counts characters, labels them bytes, and appends a marker past the limit.
Default cap 8 KB. Per-target `log_level` (`A`/`E`/`N`) applies identically to call and step rows.
Step rows written as one array `INSERT`.

### 8.4 · Retention

`ZFS_R_DYN_PURGE` — an executable report with an age parameter, its own authorization, and a
hard refusal to delete rows inside the idempotency window (documented default 30 days). It is
the **only** deletion route: `/CallLog`, `/CallStep` and `/RegistryHistory` expose no update and
no delete at all. An audit trail the audited party can edit is not one.

**Deliberately not done (YAGNI):** asynchronous logging, a separate payload table, partitioning.
The load is human-driven testing. If the log later grows, offloading payloads to a fifth table is
the next step — not now.

## 9 · Messages

`ZFS_TRM_MSG` only. Messages **017–036 are reused unchanged** — same class, same text, same
meaning — so the catalog does not fork. New numbers, allocated from
`docs/message-catalog/DS4_100_NIIF.md` (next free **037**) and written into that catalog **in the
same turn as creation**:

| No | Type | Text | Raised by |
|---|---|---|---|
| 037 | E | Request exceeds the &1 budget: &2 | `ZCL_FS_DYN_BUDGET` |
| 038 | S | Request &1 replayed from call &2 | idempotency hit |
| 039 | E | Target &1 belongs to the gateway framework and cannot be registered | self-protection (§7.1) |
| 040 | E | You are not authorized to &1 gateway targets | `ZCL_FS_DYN_AUTH` |
| 041 | E | &1 returned a business error: &2 | `BAPIRET2` scan → `BUSINESS` |
| 042 | E | Paging requires a stable sort order for &1 | `QURY` with `Skip` |
| 043 | E | Program &1 cannot be submitted: &2 | `SUBM` qualification at registration |
| 044 | S | &1 call log row(s) and &2 step row(s) deleted | `ZFS_R_DYN_PURGE` |
| 045 | E | Batch aborted at step &1: &2 | abort reason (v1 overloads 020) |

Numbers are provisional until allocation; the catalog is authoritative, and if a system read
contradicts it the system wins.

## 11 · Phasing

Each phase ends activated, ATC-clean and regression-tested. No phase leaves the service logging
to two places or half-cut-over — the failure mode that stalled the v1 split.

| Phase | Delivers | Ends with |
|---|---|---|
| 1 | Domains, data elements, the four tables, `ZFS_DYNGW`, Registry BO + DCL + behaviour pool | allow-list maintainable over OData, buffered, authorization live |
| 2 | `ZIF_FS_DYN_HANDLER`, the five handlers, `ZCL_FS_DYN_RUNTIME`/`REGISTRY`/`FACTORY`/`JSON`/`BUDGET`/`AUTH`, `ZCX_FS_DYN_ERROR`, `ZFS_FG_DYN_GW` with both RFC FMs | the engine, unit-tested in isolation, not yet reachable over HTTP |
| 3 | `ZCL_FS_DYN_DISPATCH`, `ZCL_FS_DYN_LOG`, CallLog/CallStep BOs, the eight abstract entities, `ZBP_FS_DYNGWCALLTP`, `ZFS_SD_DYNGW`, `ZFS_SB_DYNGW_O4_API`, published | **the service is live and all five kinds work end to end** |
| 4 | `ZFS_T_DYN_REGH` wiring on every route, error taxonomy surfaced in the payload, HTTP status discipline | complete audit trail; L-369 closed |
| 5 | Idempotency (`RequestId` + unique index + replay), budgets enforced, `ZFS_R_DYN_PURGE` | retryable writes are safe; retention exists |
| 6 | Docs — a new `docs/dyngw-v2-*` set, the payload file, ledger entries, `CLAUDE.md`/`AGENTS.md` index rows | contract matches reality |

Phase 3 is the first point at which the new service answers HTTP. Phases 1–3 must not be split
further.

## 12 · Risks

| # | Risk | Handling |
|---|---|---|
| 1 | RAP may refuse static actions on a read-only projection | settle with `abap_creation-run_validation` **before any create call** — a rejected shell cannot be removed (`deleteObject` denied project-wide) and would be orphaned in `ZFS_DYN_GW` permanently. Fallback: a dedicated single-row action-carrier entity with the same action URLs |
| 2 | Deep action parameters (`ExecuteBatch.Steps` as a composition) may not be supported on this release | validate with `run_validation` in phase 3 before creating the abstract entities. Fallback: `StepsJson` as a string, still one level better than v1 because each step's own fields stay typed |
| 3 | `COMMIT`/`ROLLBACK WORK` inside `ZFS_RFC_DYN_EXECUTE` flagged by ATC | expected and correct — it is outside RAP. Exempt with justification if ATC objects; the dump risk that reopened L-350 does not apply outside a behaviour implementation |
| 4 | Full table buffering on `ZFS_T_DYN_REG` delays a kill switch across app servers | buffer synchronisation is seconds, not minutes; documented. If an instant kill is required, `is_active` checks bypass the buffer on write paths |
| 5 | Delivery class `C` lets a permissive DEV allow-list reach QA/PRD | what is imported stays a per-system decision (L-335); the transport makes it possible, not automatic |
| 6 | `ZFS_TRM_MSG` is locked on another transport (L-355) | new messages go on whichever request already holds the class; the new objects go on `DS4K907263` |
| 7 | Two gateways live at once could confuse consumers | v1 is untouched and keeps its URL; v2 has a different binding name. Retirement is a separate decision after acceptance |

## 13 · Out of scope

Retiring or modifying `ZFS_SB_DYNGATEWAY_O4_API`, `ZFS_T_SLC_DYNGW` or any `ZCL_FS_SLC_GW_*`
class. Migrating v1 registry rows or call-log history. Asynchronous / long-running job execution.
Any change to the `SUBM` capture modes themselves. Repointing the existing web consoles at v2.
