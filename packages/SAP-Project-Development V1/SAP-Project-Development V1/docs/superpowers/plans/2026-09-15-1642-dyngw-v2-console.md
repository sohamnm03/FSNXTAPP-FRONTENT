# dyngw v2 Console — Phase 2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An OTTK console whose every read and write goes through the dynamic gateway v2 instead of a dedicated OData service, with a live trace panel showing the gateway's own tables filling up call by call.

**Architecture:** A ninth sibling in `web/`, identical in shape to the eight that exist: `index.html` (whole app in one file) + `proxy.py` (static server + Basic-auth/CSRF OData proxy) + `sap_config.json`. Panels 1 and 2 mirror `ottk-dttk-console` literally, fed by `RunQuery` on two CDS views. Panel 3 is new: the Gateway Trace, reading `/CallLog`, `/CallStep`, `/Registry`, `/RegistryHistory` as plain entity sets. Writes go through `ExecuteTableCrud` with `GenerateJson`, so the client never invents a key.

**Tech Stack:** Static HTML/CSS/vanilla JS in one file; Python 3 stdlib `http.server` proxy; OData V4 over `SRVD_A2X`; no build step, no package manager, no framework.

**Spec:** `docs/superpowers/specs/2026-09-15-1353-dyngw-v2-generators-design.md` §13 (Phase 2), as amended by Phase 1's live findings — see Global Constraints.

## Global Constraints

- **System:** `DS4_100_NIIF` (`DS4` / client `100`). `sap-client=100` on **every** URL including `$metadata`, or you get a 401 that looks like a bad password (L-253/L-325).
- **No ABAP objects are created or changed in this phase.** Registering a gateway target is *application data*, not a repository object, and is expected. If a task seems to need an ABAP change, **stop and report** — that is a Phase 1 gap, not something to fix here.
- **Port 8773.** Confirmed free: existing consoles occupy 8765–8772.
- **`ExecuteTableCrud` now REQUIRES `GenerateJson`.** Phase 1 added it and v2 generates action parameters `Nullable="false"`, so omitting it is an HTTP 400 `/IWBEP/CM_V4H_RUN/006` (L-341). **Always send the field**, empty string when no generation is wanted.
- **`MODIFY` is a full-row replace, not a merge (L-520).** A partial `MODIFY` silently blanks every omitted column, `LOCAL_CREATED_BY`/`LOCAL_CREATED_AT` included. This is not theoretical: it destroyed the contents of `ZOTTK_NO 100051` during Phase 1's acceptance run. **Every edit is read-modify-write, sending the complete row.** This is the single most important rule in this plan.
- **A refusal is HTTP 200 with `ExecStatus 'E'`**, never an HTTP error. The call header carries a truncated, generic message **045**; the real reason (017, 022, 035, 039, 050–054…) is on the **step row** (L-478). Read the step.
- **`Severity 'W'` + message 048** is a *partial write*, not a failure — render it as a warning that states both counts.
- **Result fields are `IsCommitted` / `IsRolledBack`**, not `Committed`/`RolledBack` — `COMMITTED` is a CDS reserved word (L-515).
- **Booleans are `Edm.Boolean`:** send unquoted `true`/`false`, never `"X"`, which is a 400 XML parse error rather than a clean refusal (L-475).
- **CURR/DEC fields are unquoted JSON numbers**, not strings (L-244).
- **Inside a batch step the `*Json` fields nest three levels deep** — build innermost-first and let the serialiser escape; message 022 cannot tell you which level broke (L-335).
- **`ZFS_T_DYN_*` cannot be registered as gateway targets** — 039 self-protection, and it is the fix for v1's privilege-escalation hole. The trace panel therefore reads `/CallLog`, `/CallStep`, `/Registry`, `/RegistryHistory` as **plain entity sets**, which is what those tables already are. It needs no registration and must not attempt one.
- **Worklog:** this is a new activity and gets its **own** file, `worklog/DS4_100_NIIF/2026-09/2026-09-15-1642-dyngw-v2-console.md`, from `worklog/_TEMPLATE.md`. Do not append to Phase 1's worklog. Follow the template's sections, adding activity-specific ones where they help — house pattern.
- **Every task ends with** the worklog updated and any new lesson appended to `lessons/lessons-ledger.md` in the same turn, continuing from the ledger's current highest number.
- **Git commits cover repo artifacts** — this phase is almost entirely repo work, unlike Phase 1.

## Task 2: Provisioning — register what the console needs, visibly

**Files:** Modify `web/dyngw-v2-console/index.html`

**Interfaces:**
- Consumes: `/api/dyngw/` from Task 1
- Produces: `dynCall()` (see Step 2), used by every later task; four registered targets

- [ ] **Step 1: Read the registry on load and gate the UI**

`GET /api/dyngw/Registry?sap-client=100`. Store the rows. Disable any action whose target is missing or `IsActive` false, with a visible reason rather than a dead button. On a system where nothing is registered the console should say so plainly, not fail obscurely.

- [ ] **Step 2: Write `dynCall()` — the wrapper every later task uses**

This sits above the reference console's `apiRequest()` and exists because **a gateway refusal is HTTP 200**, which `apiRequest()` would read as success.

```js
// A dyngw refusal is HTTP 200 with ExecStatus 'E' — apiRequest() alone would
// call that a success. dynCall throws unless ExecStatus is 'S', and surfaces
// the STEP row's message rather than the header's, because a single-shot
// action's own refusal is reported on the header as a truncated, generic 045
// ("Batch aborted at step 1: ...") while the real reason — 017, 022, 050..054 —
// is on the step (L-478).
async function dynCall(action, payload){
  const ns = 'com.sap.gateway.srvd_a2x.zfs_sd_dyngw.v0001';
  const d = await apiFetch(`/api/dyngw/CallLog/${ns}.${action}?sap-client=100`, {
    method:'POST', headers:{'Content-Type':'application/json'}, body:JSON.stringify(payload)
  });
  if(d && d.ExecStatus === 'S') return d;
  throw Object.assign(new Error(await stepMessage(d)), {dyn:d});
}
```

`stepMessage(d)` reads `d.StepsJson`/`d.RowsJson` for the per-step message and falls back to `d.MessageText` only when there is no step detail. A `Severity 'W'` with message 048 is **not** an error — it is a partial write, and must reach the caller as a warning carrying both counts.

- [ ] **Step 3: The "Provision targets" button**

One `ExecuteBatch` of four `REGI` steps. Mind the three-level `*Json` nesting inside a batch step (L-335) — build innermost-first:

| Target | Kind | Operation | Read | Why |
|---|---|---|---|---|
| `ZFS_CDS_SLC_001` | QURY | SELECT | ✓ | OTTK list |
| `ZFS_CDS_SLC_002` | QURY | SELECT | ✓ | DTTK list |
| `ZSGSLCTR_BPEXT` | QURY | SELECT | ✓ | bank lookup |
| `T000` | QURY | SELECT | ✓ | the integration guide's liveness check |

`ZFS_SLC_OTTK_BTP` is **already registered** with generation enabled — do not re-register it; `INSERT` on an existing target is refused with 035 by design.

- [ ] **Step 4: Prove the liveness check**

`RunQuery` on `T000`, `FieldsJson` `["MANDT","MTEXT"]`, `MaxRows 3`. Expect `ExecStatus 'S'`, `ResultCount 3`. This is the integration guide's own first-call check and confirms the whole path works before any business data is involved.

- [ ] **Step 5: Prove a refusal renders correctly**

`RunQuery` on `ZZ_UNKNOWN`. Expect HTTP **200**, `ExecStatus 'E'`, header message 045, **step** message 017. Confirm the UI shows the 017 text, not the truncated 045 — this is the single most common way a dyngw client confuses its users.

- [ ] **Step 6: Commit**

- [ ] **Step 2: Feed panel 1 from `ZFS_CDS_SLC_001`**

```json
{"TargetName":"ZFS_CDS_SLC_001",
 "FieldsJson":"[\"ZOTTK_NO\",\"ZSTR\",\"ZENT_ID\",\"ZTYPE\",\"ZOTTK_BANK\",\"BP_NAME\",\"ZOTTK_VALUE\",\"ZOTTK_CURR\",\"ZBUKRS\",\"BUTXT\",\"ZDATE\",\"ZOTTK_ST\",\"ZSTAT_DESC\"]",
```

## Task 4: Panel 3 — the Gateway Trace

This panel is the reason the console exists: it shows the gateway's own tables filling up as you use it.

**Files:** Modify `web/dyngw-v2-console/index.html`

**Interfaces:**
- Consumes: `dynCall()`, `loadOttk()`, `loadDttk()`
- Produces: `refreshTrace()` — called after every action in Tasks 6 and 7

- [ ] **Step 1: The counts strip**

Five counters — `CALL`, `STEP`, `REG`, `REGH`, `PROBE` — each showing an absolute count and the delta since the previous action. The delta is the point: it makes "one call wrote one log row and one step row" visible rather than asserted.

Sources, all **plain `GET`s needing no registration**:
- `CALL` / `STEP` → `/api/dyngw/CallLog?$expand=_Steps&$orderby=ExecutedAt desc&$top=50`
- `REG` → `/api/dyngw/Registry`
- `REGH` → `/api/dyngw/RegistryHistory`
- `PROBE` → `RunQuery` on `ZFS_T_TRM_PROBE` **only if** it is registered and active; otherwise show "not registered" rather than an error. It is the negative control and should stay at zero.

- [ ] **Step 2: The call log table**

One row per call: `ExecutedAt`, `Action`, `ExecStatus`, `ErrorCategory`, `ResultCount`, `DurationMs`, `Replayed`, **`IsCommitted`**, **`IsRolledBack`**, and the message. Expandable to its `_Steps` rows: `StepIndex`, `StepKind`, `TargetName`, `ExecStatus`, `Severity`, message, `ResultCount`.

Show the header message and the step message **side by side**, so the 045-vs-017 split is legible instead of confusing.

- [ ] **Step 3: Registry and history tables**

`/Registry` with `TargetKind`, `TargetName`, `IsActive`, `AllowRead`, `AllowWrite`, **`AllowGen`**, **`GenNrObject`**, `CallMode`, `MaxRows`. `/RegistryHistory` with `ChangeType`, `TargetKind`, `TargetName`, `Source`, `ChangedBy`, `ChangedAt`.

- [ ] **Step 4: Refresh after every action**

Wire `refreshTrace()` to run after provisioning, after each list load, and after every write. Capture the counts before and after so the delta is real rather than computed from a stale baseline.

- [ ] **Step 5: Commit**

## Task 6: Edit and delete — read-modify-write, never partial

**Files:** Modify `web/dyngw-v2-console/index.html`

- [ ] **Step 1: Row click opens the modal populated from a FULL read**

Do not populate from the list row — `ZFS_CDS_SLC_001` carries only 13 of the table's ~70 columns. Read the complete row first: `RunQuery` on `ZFS_SLC_OTTK_BTP` filtered to that `ZOTTK_NO`, all fields.

**This needs `ZFS_SLC_OTTK_BTP` registered as a `QURY` target as well as `TABL`.** `ZFS_T_DYN_REG`'s unique index `KND` is on *(TARGET_KIND, TARGET_NAME)*, so the same name under a second kind is permitted and does not collide. Register it with a `REGI` step; if it is unexpectedly refused with 035, **stop and report** rather than working around it.

- [ ] **Step 2: Save the WHOLE row back**

`Operation: "MODIFY"`, `ImportJson` carrying every column read in Step 1 with the user's edits applied. `GenerateJson` is `{"SysFields":"AUDIT"}` — **not** `Uuid` or `NumberRange`, both of which are refused on a `MODIFY` with 052 by design, since regenerating a key would address a different row.

**This is the rule the whole plan turns on.** A `MODIFY` carrying only changed fields blanks everything else, including `LOCAL_CREATED_BY`/`LOCAL_CREATED_AT`. It is proven, not theoretical: it emptied `ZOTTK_NO 100051` during Phase 1.

- [ ] **Step 3: Verify the audit block survived**

After an edit, read the row independently and confirm `LOCAL_CREATED_BY`/`LOCAL_CREATED_AT` are **unchanged** and `LOCAL_LAST_CHANGED_AT` advanced. If created-by is blank, the read-modify-write is broken — **stop and report**, do not patch the row.

- [ ] **Step 4: Delete — key on `UUID`, and treat a zero count as failure**

`Operation: "DELETE"`, `GenerateJson` **empty** (any non-empty `GenerateJson` on a `DELETE` is refused with 052). Confirm behind a modal, and state that the ticket's number is not returned to the sequence.

**`ImportJson` must carry `UUID`, not just `ZOTTK_NO`.** The table's real primary key is `CLIENT` + `UUID` + `ZOTTK_NO`; `ZOTTK_NO` alone is a business/display field. Phase 1 hit this live: a delete sent with only `ZOTTK_NO` matched nothing, deleted nothing, and returned **`ExecStatus 'S'` with `ResultCount 0`** — a silent no-op reported as success (L-522). The `UUID` comes from Step 1's full read; `ZFS_CDS_SLC_001` does not carry it, so the list row alone is never enough to delete from.

**Treat `ResultCount 0` on a delete as a failure and say so.** The gateway reports a key that matched nothing as success, so the console must not. Show "nothing was deleted — the key did not match" rather than a success toast, and leave the row in the list.

- [ ] **Step 4a: Prove the zero-count path is handled**

Deliberately issue a delete for a `UUID` that does not exist and confirm the UI reports a failure, not a success. This is cheap, destroys nothing, and is the only way to know the guard works — the same discriminating-test discipline Phase 1 used throughout.
