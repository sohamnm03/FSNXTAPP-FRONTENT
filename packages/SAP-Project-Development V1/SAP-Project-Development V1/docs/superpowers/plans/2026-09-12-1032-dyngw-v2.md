# Dynamic Gateway v2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a new, generic, allow-listed OData V4 gateway — dynamic FM/BAPI calls, table CRUD, SELECT queries, report execution and target registration — from scratch in package `ZFS_DYN_GW`, with a real rollback, a real audit trail and a real authorization model.

**Architecture:** A thin RAP layer over a dedicated `DESTINATION 'NONE'` execution session. The session owns the business LUW, so `COMMIT`/`ROLLBACK WORK` are legal inside it; the call/step log is written afterwards in the RAP LUW and committed by RAP's own save. Two LUWs is what lets rollback and durable failure-logging coexist — the thing v1 structurally cannot do. Inside the session, a two-phase dispatcher (`prepare` every step, then `execute` every step) drives five handlers behind one interface, with a single class holding every dynamic statement.

**Tech Stack:** ABAP on S/4HANA on-premise (`DS4`/100), RAP managed BOs, CDS view entities + abstract entities, OData V4 (`SRVD_A2X`), `/ui2/cl_json`, ABAP Unit, ATC. No local build — every verification runs on SAP over MCP.

**Spec:** `docs/superpowers/specs/2026-09-12-1033-dyngw-v2-design.md`

## Global Constraints

- **System:** `DS4_100_NIIF` (`DS4` / client `100`). Confirm before any write — the Logon Pad also holds two production entries.
- **Package:** `ZFS_DYN_GW`. **Transport:** `DS4K907263`. No `$TMP`, ever.
- **Routing (project rule 5):** `adt-mcp` **creates**; `mcp-abap-abap-adt-api` **changes** and does **all reads**. A creation falls back to `mcp-abap-abap-adt-api` only when `adt-mcp` genuinely cannot do the type — and the reason goes in the worklog.
- **Naming gate (project rule 1):** record `NAMING: <name> -> matches <pattern row>` **before** every create call. Every name is pre-validated in spec §4. On any mismatch: stop and ask.
- **Never create an object the human didn't ask for** (project rule 3). No helper, runner, scratch or test objects. If a step cannot be done with the objects in this plan, stop and report.
- **Messages:** `ZFS_TRM_MSG` only. Reuse 017–036 unchanged. New numbers from `docs/message-catalog/DS4_100_NIIF.md` (next free **037**), written into that catalog **in the same turn** as creation.
- **Text elements:** never via ADT or `INSERT TEXTPOOL`. Only the `sap-gui` script in `docs/sap-gui-object-automation.md` (SE38). Applies to Task 19's report.
- **No draft** on any BO (decision 8).
- **ABAP idiom traps that will cost you a `-32603` save failure:**
  - **Never** write `TYPE c LENGTH n` inline in a method's `IMPORTING`/`EXPORTING`/`CHANGING`/`RETURNING` list. Declare a named `TYPES` alias first and reference it (L-373/L-375). This applies to every signature in this plan.
  - `abap_func_parmbind_tab` is **hashed** — `INSERT ... INTO TABLE`, never `APPEND` (L-308).
  - A CDS `where` clause goes **after** the `{ }` field list, not before it (L-241).
  - `define view entity` refuses a classic DDIC `VIEW` as a source — use the released `I_*` replacement (L-240).
- **Activation:** activate a program and all its includes in **one** `activateObjects` call (L-209).
- **Publishing:** `publishServiceBinding` reports success without publishing. Publish with `scripts/sap-gui-publish-service.py --group-id <binding> --yes`; its `"ok"` is the verification (L-220/L-232).
- **Live HTTP tests:** PowerShell, **sandboxed** (L-318). `sap-client=100` on every URL including `$metadata` (L-253/L-325). PowerShell 5.1 `ConvertTo-Json` collapses a 1-element array to an object — build arrays by hand (L-315).
- **Every task ends with:** the worklog `worklog/DS4_100_NIIF/2026-09/2026-09-12-1034-dyngw-v2-framework-design.md` updated (object list row + todo tick) and any new lesson appended to `lessons/lessons-ledger.md` **in the same turn**.
- **Git commits** cover repo artifacts only (worklog, docs, scripts). ABAP source lives on SAP; `DS4K907263` is its version control.

## External prerequisites — BLOCKED, needs the human

### P1 · Authorization object `ZFS_DYNGW` (blocks Task 5, Task 14)

**Neither MCP server can create an authorization object.** `SUSO` is absent from
`adt-mcp`'s creatable-object list, and `sap-gui` creation is restricted to text elements and
transaction codes (project rule 5 / L-229). SU21 is therefore not a route this project permits an
agent to take. **A human must create it**, then say so; every dependent task is otherwise blocked.

Exact definition required:

| Property | Value |
|---|---|
| Object name | `ZFS_DYNGW` |
| Class | any suitable custom class (e.g. `ZZ` / `BC_A`) |
| Field 1 | `ACTVT` (standard) — permitted values `01` create, `02` change, `03` display, `16` execute |
| Field 2 | `ZDYNKIND` — new field, `CHAR(4)`, values `FUNC` `TABL` `QURY` `SUBM` `REGI` `*` |
| Field 3 | `ZDYNTGT` — new field, `CHAR(30)`, target name or pattern, `*` allowed |

Permission mapping the code will check:

| Permission | `AUTHORITY-CHECK` |
|---|---|
| `ADMIN` | `ACTVT` in (`01`,`02`) — maintain the allow-list, any route |
| `EXECUTE` | `ACTVT` = `16`, plus `ZDYNKIND` and `ZDYNTGT` of the call |
| `AUDIT` | `ACTVT` = `03` — read the log |

**Until P1 is delivered, Tasks 1–4 and 6–13 proceed unchanged.** Task 5 (DCL + behaviour-pool
authorization) and Task 14 (`ZCL_FS_DYN_AUTH`) stop at the `AUTHORITY-CHECK` statement, which will
not compile against a non-existent object. Do not substitute a different object, and do not
reintroduce a compiled policy constant in its place — that is the v1 pattern this build exists to
replace.

### P2 · Domain / data element creation route (blocks Task 1)

`adt-mcp` cannot create `DOMA` or `DTEL` either. Unlike P1 this has a legitimate fallback under
routing rule 5: `mcp-abap-abap-adt-api`'s `createObject`. **Task 1 Step 1 establishes which route
works before anything is created.** If neither server can create them, that is a spec amendment —
stop and ask, do not silently switch the tables to built-in types.

  callee's behaviour behind the caller's back (L-311).

not roll anything back on its own.

`build_call`'s signature — an inline `TYPE c LENGTH 20` there fails the save (L-375, found on
